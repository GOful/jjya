# Supabase 공유 DB

익명 접속을 사용하므로 로그인 화면 없이 같은 점검 내용·일지·횟수를 공유합니다.
사이트를 아는 누구나 공유 데이터를 읽고 수정할 수 있습니다.

## 이미 설정한 프로젝트: 이번 변경 적용

Supabase **SQL Editor → New query**에서 [migrate-normalized.sql](migrate-normalized.sql)
전체를 붙여넣고 **Run**을 누릅니다. 완료 후 웹사이트를 새로고침합니다.

- 기존 `app_catalog`의 편집된 내용을 행 단위 테이블로 옮깁니다. 기본 데이터로 덮어쓰지 않습니다.
- 기존 일지·사용 횟수·항목 ID를 유지합니다.
- 기존 JSON 테이블은 복구용으로 `jjya_archive.app_catalog_legacy`에 옮깁니다. 앱은 이 테이블을 사용하지 않습니다.
- 전체 마이그레이션은 한 트랜잭션입니다. 실패하면 변경을 취소합니다. 재실행해도 새로 편집한 행을 덮어쓰지 않습니다.
- 앱은 마이그레이션 전 구형 DB에도 연결되지만, 정확한 최근 복사 상태 보존은 마이그레이션 후부터 지원합니다.

## Table Editor에서 볼 테이블

| 테이블 | 내용 | 편집할 열 |
| --- | --- | --- |
| `risk_trainings` | 위험예지훈련 23개, 한 항목당 한 행 | `categories`, `risk_text`, `safety_rules` |
| `inspection_types` | 안전점검 종류 6개 | `name`, `reference_period` |
| `inspection_items` | 안전점검 세부 항목 46개 | `content` (`type_id`로 종류 연결) |
| `misc_tasks` | 기타업무 7개 | `title`, `log_text` |
| `work_logs` | 현재 저장된 업무일지 | 앱의 복사 버튼으로 자동 저장 |
| `work_log_copies` | 복사 당시 본문·선택 항목·날짜 | 앱에서 자동 기록 |
| `copy_events` | 중복을 제외한 사용 이력 | 앱에서 자동 기록 |
| `catalog_revision` | 동시 편집 방지용 변경 버전 | 자동 관리 |

ID와 항목 번호는 기존 횟수/선택 기록과 연결됩니다. 기존 항목의 내용을 수정하는 용도이며,
행 삭제·ID 변경·항목 추가는 현재 앱에서 지원하지 않습니다.
Table Editor에서 내용을 바꿔도 변경 버전이 자동 갱신됩니다.
`reference_period`는 과거 공문의 참고 문구이며 일지의 시작일·종료일은 해당 일지에서 입력합니다.

횟수는 다음 읽기 전용 뷰에서 항목 이름과 함께 확인합니다.

- `risk_training_usage`: 위험예지훈련 이름·분류·사용 횟수
- `inspection_item_usage`: 점검 종류·항목 번호·내용·사용 횟수

점검 내용은 JSON에 보관하지 않습니다. API 응답에서만 기존 화면에 맞는 형태로 묶습니다.
`work_logs.state`, `work_log_copies.state`의 JSON은 화면 선택 상태를 복원하기 위한 스냅샷입니다.

## 최근 복사 상태 복원

- 사이트 진입 시 **가장 최근 복사한 일지**의 본문·선택 항목·날짜를 복원합니다.
- 이후 저장만 한 초안이 더 최신이어도 마지막 복사 상태를 우선합니다.
- 아직 복사한 기록이 하나도 없으면 최근 저장된 일지를 불러옵니다.
- 복사 시점은 매번 별도로 보존하지만, 사용 횟수는 같은 일지/항목당 한 번만 증가합니다.
- 복사된 일지를 이후 다른 사람이 수정했다면, 과거 복사 상태를 다시 저장할 때 버전 충돌을 알립니다.
  필요한 본문을 따로 복사해 둔 뒤 새로고침합니다.
- 구형 DB에는 복사 당시 스냅샷이 없으므로 과거 상태를 완벽하게 되살릴 수는 없습니다.
  마이그레이션 때 기존 복사 이력이 있는 일지의 **현재 상태**를 한 번 보존하며,
  이후 새로 복사한 상태부터 정확하게 보관합니다.

## 새 프로젝트 설정

1. SQL Editor에서 [setup.sql](setup.sql) 전체를 실행합니다. 기존 프로젝트에서는 위의 마이그레이션 파일을 사용합니다.
2. Authentication 설정의 **Anonymous Sign-Ins**를 활성화합니다.
3. `supabase-config.js`에 Project URL과 Publishable key(또는 anon public key)를 설정하고 `enabled: true`로 둡니다.
   secret/service_role 키나 DB 비밀번호를 브라우저 설정에 넣지 않습니다.

## 저장·공유 방식

- **복사**만 사용합니다. 클립보드 복사와 공유 DB 저장을 함께 수행하며 처음 복사하는 일지/항목만 집계합니다.
- 같은 일지를 다른 PC에서 다시 복사해도 횟수를 중복 집계하지 않습니다.
- 다른 위험예지훈련을 선택하면 새로운 일지를 시작합니다. 같은 항목의 새 일지는 선택 취소 후 다시 선택합니다.
- 최근 복사 날짜는 상단에 표시합니다. 다음 접속 시 최근 복사한 본문·선택 항목·날짜를 자동 복원합니다.
- 별도의 새 일지·일지 저장·이력 불러오기·횟수 새로고침 버튼은 없습니다.
- 다른 사용자의 복사 결과와 사용 횟수는 페이지를 새로고침하면 확인할 수 있습니다.
- 점검 내용은 Supabase Table Editor에서 수정합니다. 위험예지훈련은 웹페이지의 내용 수정 메뉴에서도 수정할 수 있습니다. 새로고침하면 반영됩니다.
- 서버 저장 실패 시 현재 본문과 이전 최근 복사 날짜를 유지하고 오류를 표시합니다. 개인 저장으로 몰래 대체하지 않습니다.
- 브라우저에 있던 개인 사용 횟수는 DB로 자동 합산하지 않습니다.

## 검증

```sh
npm ci
npm test
python tests/browser_shared.py
```

SQL 검증은 PGlite(PostgreSQL WASM), 브라우저 검증은 Playwright Python/Chromium과 모의 Supabase API를 사용합니다.
WASM이 제한된 환경에서는 제한 해제 후 실행하고 실제 이름이 있는 SQL 테스트 2개가 모두 통과했는지 확인합니다.
실제 Supabase 설정·연결 검증은 별도로 필요합니다.

## 서무업무

서무업무는 `misc_tasks.id = 7`이며, 선택 시 `* 분소행정업무처리`가 스트레칭 바로 아래에 들어갑니다.
기존 6개 항목만 있는 DB에도 화면에서 기본 항목을 보완하므로 바로 사용할 수 있고 선택 상태는 일지에 함께 저장됩니다.
DB에서도 이 항목을 관리하려면 정규화가 끝난 프로젝트의 SQL Editor에서 [add-office-task.sql](add-office-task.sql)을 한 번 실행합니다.
새 프로젝트 설정과 정규화 마이그레이션 파일에는 해당 행이 포함되어 있습니다. 기존 1~6번 항목 ID는 유지합니다.

## 갑조·을조·병조 분리

기존 프로젝트에서는 SQL Editor에 [migrate-teams.sql](migrate-teams.sql) **전체**를 붙여넣고 실행합니다.
기존 정규화 여부와 관계없이 적용하도록 구성했으며, 전체 변경은 한 트랜잭션입니다.
신규 프로젝트용 `setup.sql`에는 조별 설정이 포함되어 있습니다.

- 기존 일지·횟수·복사 이력은 갑조로 배정합니다. 삭제하거나 횟수를 0으로 초기화하지 않습니다.
- 을조·병조는 별도 횟수로 시작합니다.
- `risk_trainings`, `inspection_types`, `inspection_items`, `misc_tasks` 내용은 세 조가 공통 사용합니다.
- `work_logs.team`, `work_log_copies.team`으로 조를 구분합니다. `copy_events`의 조는 연결된 일지로 결정됩니다.
- 상단 탭으로 선택한 조의 횟수를 표시·정렬하고, 복사 시 그 조만 집계합니다.
- 최근 복사 상태와 날짜도 조별로 복원합니다. 브라우저는 마지막 선택한 조를 기억합니다.
- 같은 일지 재복사는 중복 집계하지 않습니다. 다른 조의 일지를 잘못 수정하려는 요청은 거절합니다.
- 조를 바꾸기 전 작성하던 미복사 내용은 같은 페이지가 열려 있는 동안 임시 보관합니다. 페이지 종료 후에는 복사한 기록만 복원됩니다.
- 누구나 다른 조로도 자유롭게 이동할 수 있습니다. 탭은 기록 분류 기능이며 사용자 접근 권한을 제한하는 기능은 아닙니다.
- SQL 적용 전에는 갑조의 기존 기능을 유지하고 을조·병조 버튼을 잠급니다. 적용 후 새로고침하면 해제됩니다.
- 기존 버전 사이트의 호출은 갑조로 처리하여 새 조의 기록과 섞이지 않게 유지합니다.

조별 횟수를 Table Editor에서 확인하려면 다음 뷰를 사용합니다.

| 뷰 | 내용 |
| --- | --- |
| `team_risk_training_usage` | `team`, 위험예지훈련, 분류별 횟수 |
| `team_inspection_item_usage` | `team`, 점검 종류, 항목별 횟수 |

조별 함수 및 트리거만 다시 적용할 경우에는 `team-schema.sql`을 사용합니다.
전체 구조가 없는 최초 전환에는 반드시 `migrate-teams.sql` 또는 신규 프로젝트용 `setup.sql`을 사용합니다.

## 횟수 직접 수정

기존 프로젝트는 SQL Editor에서 [migrate-count-editing.sql](migrate-count-editing.sql) 전체를 실행합니다.
조별 설정을 아직 적용하지 않았어도 이 파일에 포함되어 있으며, 기존 기록과 수동 보정값을 보존합니다.
신규 프로젝트용 `setup.sql`에는 포함되어 있습니다.
조별 설정이 이미 완료된 경우에는 `count-editing-schema.sql`만 실행해도 됩니다.

1·2번 영역의 **횟수 수정**을 누르면 횟수 옆에 `− / +`가 나타납니다.
매 클릭마다 선택한 조와 항목의 횟수를 자동 저장합니다. 별도 저장이나 복사는 필요 없습니다.
0 미만으로 내릴 수 없으며, 최근 복사 날짜나 선택한 일지는 바뀌지 않습니다.
수정 중에는 목록 순서를 고정하고 **수정 완료** 후 사용 횟수 내림차순으로 다시 정렬합니다.

보정값은 `usage_adjustments`에 별도 기록되며 원본 `copy_events`는 삭제하지 않습니다.
실제 표시값은 복사 횟수와 보정값의 합계입니다. `effective_usage_counts`와
조별 횟수 뷰에서도 같은 값을 볼 수 있습니다.
기존 일지를 다시 복사하면 중복 집계하지 않으며, 새로운 일지를 복사하면 수정된 횟수에서 1회 증가합니다.
요청을 재시도해도 같은 수정이 중복 적용되지 않도록 요청 ID를 사용합니다.
서버 저장 실패 시 화면의 기존 횟수를 유지하고 오류를 표시합니다. 같은 버튼을 다시 누르면 해당 요청을 재시도합니다.

## 로딩 최적화

유효한 익명 세션은 매 접속마다 사용자 확인 요청을 보내지 않고 재사용합니다.
실제 데이터 조회는 서버가 토큰을 검증하며, 거부된 세션은 한 번 재연결합니다.
공통 점검 내용, 조별 횟수, 최근 복사 상태는 동시에 조회합니다.
공통 점검 내용만 현재 페이지에서 최대 60초간 재사용하고, 같은 조회가 겹치면 한 요청으로 합칩니다.
조별 횟수와 복사 상태는 매번 서버에서 새로 조회합니다. 페이지를 새로고침하면 점검 내용 캐시도 비워집니다.
이 개선에는 추가 SQL 적용이 필요하지 않습니다.

## 위험예지훈련 내용 수정 메뉴

1번 위험예지훈련 제목 옆 **내용 수정**을 누릅니다.
항목을 선택하고 **위험예지훈련 내용**, **작업 전 안전수칙**을 수정한 뒤 **저장**을 누릅니다.
수정값은 `risk_trainings.risk_text`, `risk_trainings.safety_rules`에 저장하며 갑조·을조·병조에 공통 적용됩니다.
다른 브라우저는 새로고침하면 갱신됩니다. 항목 ID·분류·조별 사용 횟수·이전 복사 기록은 변경하지 않습니다.
작성 중인 업무일지도 유지하며, 바뀐 내용은 새로 생성하는 일지부터 사용합니다.
같은 항목을 다시 생성하려면 선택 취소 후 다시 선택합니다.

기존 `save_app_catalog` 저장 함수를 사용하므로 이번 메뉴를 위한 추가 SQL은 없습니다.
저장할 때 최신 항목과 변경 버전을 다시 확인하고 JSON 본문으로 전달합니다.
정규화된 DB에서는 각 항목 행을 갱신하며, 구형 DB도 기존 저장 함수로 호환합니다.
동시 수정 충돌이나 서버 오류가 나면 입력을 유지하고 오류 종류를 표시합니다.
두 사람이 동시에 같은 항목을 수정하면 먼저 저장된 값을 덮어쓰지 않고 오류를 표시합니다.
이때 입력한 내용은 지우지 않습니다. 내용을 따로 복사한 후 창을 닫고 다시 열어 최신 항목을 확인합니다.

## 안전점검·기타업무 내용 수정 메뉴

- **2. 기간별 안전점검 → 내용 수정**: 점검 종류와 항목을 선택해 세부 점검 내용을 수정합니다.
- **3. 기타업무 → 내용 수정**: 업무를 선택해 표시 이름과 업무일지에 들어갈 문구를 수정합니다.

두 메뉴 모두 갑조·을조·병조 공통 항목에 저장합니다. 항목 ID/순서와 조별 횟수는 유지하며,
작성 중인 본문이나 이전 복사 기록은 바꾸지 않습니다. 수정값은 새로 생성하는 일지부터 사용합니다.
다른 PC는 새로고침하면 반영됩니다. 기존 `save_app_catalog` 함수를 사용하므로 추가 SQL은 필요 없습니다.
입력한 내용은 저장 실패 시 유지하며 동시 수정은 충돌로 안내합니다.

이전에 서무업무를 화면 기본값으로만 사용하고 DB에는 등록하지 않은 프로젝트는
서무업무 수정 전에 `add-office-task.sql`을 실행해야 합니다. 이후 전체 마이그레이션에는 해당 행이 포함되어 있습니다.
